# RadarScope 总体计划

> 这份文档回答一个问题：**这个软件接下来往哪走、按什么顺序走、怎么算走完了。**
> 不是功能清单，是决策记录。有分歧的时候以这里的原则为准。

- 版本：v1.1.0（2026-11-26，见 [ROADMAP.md](ROADMAP.md)——B1~B3、C1~C4、D1~D6、A5 夹具与模拟电子站已全部落地）
- 定位：**通用雷达显控台**，适配多种雷达模块与多种项目场景，不绑定任何厂商型号
- 不在定位内：军用火控、适航认证、气象业务运行系统

> 以下第一节保留 v0.4 初始里程碑档案；最新实时进展与后续排期以 [ROADMAP.md](ROADMAP.md) 为准。

## 二、设计原则（改代码前先读这五条）

1. **通用性建在数据形态上，不建在设备上。**
   所有雷达的输出归到 `scan 矩阵` 与 `targets 目标列表` 两种原料，互相可推导。
   新设备只要能填其中之一就能接进来。

2. **能力声明驱动界面，不按型号写分支。**
   界面显示什么由 `Capabilities` 决定。代码里**任何地方都不许出现
   `if 型号 == "LD2450"` 这种判断**——型号只是显示用的字符串。

3. **分层单向依赖。**
   传输 → 协议 → 驱动 → 数据 → 处理 → 呈现。下层不认识上层。
   UI 里出现 `serial` 或 `struct.unpack` 就是分层破了。

4. **告警、标定这类"人机协作"功能，必须能在界面上走完。**
   只有 API 没有人机界面，等于没做。

5. **宁可少一个功能，不留一个坑。**
   每个已知缺陷都要么修掉、要么写进限制表，不许"先这样"。

## 三、分类体系（界面的骨架）

型号天天出新，写进逻辑就把软件钉死在某一年。所以按**两个正交维度**分类：

### 维度一：数据源（`source`）

| 值 | 含义 | 界面分栏 |
|---|---|---|
| `sim` | 程序内部生成，不需要硬件 | 模拟与演示 |
| `device` | 真实硬件 | 实测模块 |
| `fusion` | 多台设备组合 | 多设备融合 |
| `replay` | 录制数据回放 | 数据回放 |

### 维度二：测量形态（`form`）

| 值 | 含义 | 典型 |
|---|---|---|
| `point` | 单点测距，只有距离，无方位分辨 | LD2410、单波束测距 |
| `sector` | 受限扇区扫描（<360°） | LD2450、超声波+舵机 |
| `omni` | 全向 360° | 机械旋转、电子扫描 |
| `tracking` | 直接给目标坐标 | 跟踪雷达 |
| `rd` | 相干处理，含距离-多普勒 | 相控阵、FMCW |
| `fusion` | 多设备组合输出 | 6×60° 组网 |

界面 = `数据源` 下拉框 + `类型` 下拉框（按形态分组，组标题不可选）。
型号只出现在条目文字里，**不参与任何判断**。

新增一块雷达时，先问：它的 `source` 和 `form` 是什么？
答不上来说明还没理解它，别急着写驱动。

## 五、优先级判断方法

按 **影响面 × 依赖度** 排，不按"酷不酷"排：

1. 影响所有使用者的（启动、崩溃、性能）→ 立刻
2. 影响新设备接入的（驱动、标定、插件）→ 优先
3. 只影响特定场景的（GIS、3D、气象）→ 排后
4. 需要外部硬件的 → 等硬件到位再做，不要先写猜的代码

反例：先做 3D 点云没用——没有能吐原始 ADC 的板子，做了也验证不了。

## 六、参考与借鉴（避免重复造轮子）

搜过同类开源项目，确认哪些值得抄、哪些没必要：

| 项目 | 是什么 | 借鉴什么 | 不抄什么 |
|---|---|---|---|
| **TI mmWave Industrial Visualizer**（Python 版） | TI 官方毫米波可视化 | TLV 协议分层解析、UART 双口（配置口+数据口）做法 | 只支持自家芯片，扩展性差 |
| **RadarStream**（IWR6843 + DCA1000） | 原始数据采集与多维可视化 | RTI/DTI/RDI/RAI 多维视图的分法 | 依赖 DCA1000 硬件，门槛高 |
| **OpenRadar** | TI 雷达 DSP 开源库 | 距离/多普勒 FFT、CFAR、角度估计的实现细节 | 纯算法库，无界面 |
| **Exodus Radar**（船用 PPI） | Raymarine 雷达全屏显示 | **"面板由雷达声明的能力生成"**（与我们 Capabilities 同思路）、head-up/north-up、点击测距、trail | 绑定 Quantum 型号、tkinter 实现 |
| **PyCINRAD** | 中国气象雷达解码与可视化 | PPI/剖面绘图、色标体系、速度退模糊 | 面向气象基数据格式 |
| **ahinkka/ppi** | 浏览器端气象 PPI | 重投影、产品动画、色标可切换 | Web 技术栈，与桌面端路线不同 |
| **Flight Radar Widget** | 桌面 PPI 挂件 | 点击 blip 出详情卡的交互、主题化 | 数据源是 OpenSky，无雷达硬件 |

**结论**：我们的差异化在"驱动/传输/协议三层解耦 + 能力声明 + 多站融合"，
这几个方向现有开源项目都没有做好。显示层与交互层可以大量借鉴，不必自研。

## 七、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 型号爆炸导致驱动泛滥 | 维护成本失控 | 分类只认形态；同形态复用驱动 + 参数化协议 |
| 融合性能随设备数下降 | 6 台 19fps，12 台可能掉到 10fps | 降到 10Hz 出图 + 传感器帧率独立；必要时挪到 numpy 之外 |
| 标定被跳过 | 融合画面"看着对，位置全错" | 界面显式提示未标定；盲区与残差可见 |
| 过度设计 | 增加复杂度却没解决真问题 | 每个抽象必须有两个以上实现才保留 |
| 单人维护断档 | 后续无人接手 | 本文档 + `HANDOVER.md` + 测试即规格 |

## 八、明确不做

- 不做军用火控/武器接口
- 不做适航/车规认证
- 不做云端多租户 SaaS（可导出数据，但不做账号体系）
- 不为单一型号做定制分支
- 不追 UI 动效，优先信息密度与响应速度

### 已知的显示瑕疵

- **瀑布图在 6 站融合下偏亮**：`range_profile` 取"各方位最大值"，
  目标被抹宽 + 多站叠加，整片接近峰值。真正的修法不是调 gamma，
  而是改成"每个航迹一条距离轨迹线"或"按方位分块显示"。
