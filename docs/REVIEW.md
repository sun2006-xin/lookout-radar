# 多角度审查报告

> 2026-11-25 · 对照当前 main 分支（57 文件 / 11402 行）
> 审查方式：分五个视角独立过一遍代码与设计，再汇总。每个视角只关心自己那类问题，
> 避免"什么都看一眼、什么都不深"。

| 视角 | 关注点 | 结论 |
|---|---|---|
| ① 可靠性 / 并发 | 线程、异常、资源释放 | 🟡 可用，有 3 处需加固 |
| ② 安全 / 健壮性 | 输入校验、路径、网络 | 🟢 风险低 |
| ③ 可用性 / UX | 误操作、可发现性 | 🟡 已明显改善，仍有 2 处 |
| ④ 架构 / 可维护性 | 分层、耦合、命名 | 🟢 结构清晰，1 处技术债 |
| ⑤ 产品 / 定位 | 落地场景、竞品差异 | 🟡 需要选定一个主战场 |

## ① 可靠性 / 并发

### R1 【中】32 处 `except Exception:` 里，有 6 处是静默吞掉

```
radarscope/core/aisfeed.py:58       socket.close() 失败
radarscope/core/forwarder.py:79     sendto 失败（已记 last_error）
radarscope/core/storage.py:127/338  SQLite 提交失败
```

网络与设备类异常吞掉是**刻意的**（雷达不能因为地图拉不到就崩），
但 `storage` 那两处会把"航迹没写进库"变成无声事件 —— 用户以为在记录，其实没记。

**建议**：`storage` 的写失败要计数并在状态栏暴露一个"存储异常"指示，而不是只写日志。

### R2 【中】UI 线程里有一处阻塞调用

```
radarscope/ui/linkdialog.py:364   time.sleep(0.02)   # 测试连接时读端口
```

最长 1.2 秒。对话框里可接受（用户点了"测试"就是在等），但**没有"取消"**。
**建议**：改成 QTimer 驱动的非阻塞轮询，或者至少加进度提示。

### R3 【低】地图下载线程没有取消机制

`MapLayer._Fetcher` 用 `isInterruptionRequested()` 检查，但没人调用 `requestInterruption()`
（切图源 / 关闭地图时）。最坏情况后台还在拉 24 块瓦片，不影响正确性。
**建议**：`_start_fetch` 前先 `self._thread.requestInterruption()`。

### R4 【低】`AisFeed.stop()` 依赖 socket 超时退出

`join(timeout=1.5)` 后线程可能还活着（一次 `recvfrom` 最长 0.5s，通常够）。
真正的隐患是 `running=False` 后仍有 `_targets` 写入 —— 无害但应该加锁保护（已有锁）。

**这一项没发现数据竞争**：所有共享结构（`_targets`、`_cflat`、`_trails`）
都在同一线程写、或被锁包住。相机没白搭。

## ② 安全 / 健壮性

### S1 【中】UDP 转发没有目标校验

`Forwarder` 接受任意 `host:port`，包括公网地址。这是特性也是风险：
一台机器被误配置成往公网广播目标数据。
**建议**：默认限制为私网/环回网段，公网地址要求二次确认。

### S2 【低】瓦片缓存无大小上限

`data/tiles/` 会随浏览范围无限增长（每块约 10 KB，看遍一个城市约 50 MB）。
**建议**：加 LRU 或"超过 200 MB 清理最旧"。

### S3 【低】插件是任意代码

`plugins/*.py` 直接 `exec` 模块加载 —— 这是**设计如此**（插件要能注册驱动与规则）。
但界面上要有明确提示："只加载你信任的插件"。
**当前**：插件管理对话框里有说明，但没有视觉警示。建议加黄条。

### S4 【无风险】SQL 全部参数化

`storage.py` 里所有查询都用 `?` 占位，没有字符串拼接。
`query_events` 的动态条件也是追加占位符，安全。

## ③ 可用性 / UX

### U1 【中】画警戒区与删除共用右键

`ppi.mousePressEvent` 在 `zone_mode` 下右键 = 删除最近一个区。
已加二次确认，但**语义仍然怪**：右键在雷达显示里是 EBL，在这里是删除。

**建议**：改成"右键选中某个区 → 高亮 → Delete 键删除"，或者干脆只允许在规则表里删。
"最近一个"在区多了以后基本不可预测。

### U2 【中】`--selftest` 只有命令行，界面上没有入口

普通用户不会开终端。**建议**：帮助菜单加「自检」，把结果打到事件日志。

### U3 【低】状态栏信息密度不均

左侧"融合 | 目标 5 | 6 × 60° 全向融合"很长，右侧 CPA + fps 挤在一起。
**建议**：CPA 单独一栏并加图标；或把"融合模式"移到工具栏。

### U4 【已修】此前的三个问题

- 「设…」看不懂 → 改名「连接设置」
- 菜单里的设置面板点不动（QWidgetAction 需要焦点）→ 改独立对话框
- 工具栏三行拥挤 → 收敛两行 + 设置对话框

## ④ 架构 / 可维护性

### A1 【中】`mainwindow.py` 已到 1400 行

它是唯一知道"所有部件怎么连"的地方，继续长下去会变成上帝对象。
**建议**：把"连接与重连"、"告警条与静音"、"录制与转发"三块拆成三个 mixin / 控制器类。

### A2 【低】`Capabilities` 与驱动类属性双轨

`source/form/vendor` 既是类属性又要同步进 `Capabilities`（之前在 `_connect` 里手工补，
漏了一次就出了"共视列不显示"的 bug）。
**建议**：`capabilities()` 用 `dataclasses.replace` 一次性合并类属性，杜绝手工同步。

### A3 【好】数据模型集中

`RadarFrame` 只有 timestamp / scan / az_axis / r_axis / meta 五个字段，
所有驱动都收敛到它。这是整个项目最值钱的设计决定 —— **换设备不用换界面**。

### A4 【好】测试不 mock

20 组测试直接跑真实算法和真实 SQLite，覆盖了切帧、CFAR、融合、交会、CRC、AIS 解码、
地图换算。这类测试才拦得住回归。

## ⑤ 产品 / 定位

### P1 【关键】现在有两个战场，最好只选一个

- **A. 教学/DIY**：拿来做课设、毕设、树莓派/STM32 雷达项目。要的是"插上就有画面"。
- **B. 工程交付**：多站组网、告警、留证、交付给甲方。要的是稳定、审计、报表。

两个战场的优先级互相冲突（A 要轻、要多设备；B 要稳、要少而深）。
**建议**：以 A 为入口（保留全部驱动与模拟器），以 B 为深度（把告警+留证做扎实）。

### P2 【优势】"形态而非型号"是真差异点

国内同类上位机大多绑定自家模块。瞭望的驱动模型让"换设备不改界面"成立，
这是可以写进一句话介绍的东西 —— README 已经这么写了。

### P3 【短板】没有"第一眼惊艳"

雷达类软件的第一印象来自画质与动态。当前 PPI 的余晖、拖尾已经有了，
但**缺一个能直接甩给别人的动态演示**（GIF/短视频）。README 里放一段 10 秒循环，
转化率会完全不同。

### P4 【风险】数据转发协议没有版本号

`{"type":"radarscope.frame"}` 是唯一的协议标识。字段一改，老接收端静默错位。
**建议**：加 `"v":1`，并承诺"新增字段不删旧字段"。

| P2 | S1 转发目标限制；S2 缓存上限；P3 演示动图 | 小 |
| P3 | A2 Capabilities 合并；U2 界面内自检；U3 状态栏重排 | 小 |

## 一句话结论

**架构是干净的，问题集中在"边界情况的可见性"上** ——
失败被静默吞掉、配置改错没有反馈、删东西太容易。
把这几处补上，它就是一个可以放心交给别人用的工具，而不是一个"作者自己能用"的项目。
