# ADR-0001：语言选型与"要不要用 Rust 重写"

- 状态：已采纳
- 日期：2026-11-25
- 决策者：项目维护者
- 影响范围：全部代码

---

## 背景

有人提出"Rust 很优秀，可以重构成 Rust"。这是个合理的疑问，但必须用数据回答，
不能用偏好回答。所以先量，再决定。

当前规模：约 7700 行 Python、9 个驱动、13 组测试、已有可运行的 Windows exe。

---

## 实测数据（Intel Core i7-13xxx / Windows 11 / Python 3.13 / numpy 2.5）

### 修复前：每帧固定开销 24.93 ms（20 fps 预算 50 ms，占用 50%）

| 环节 | 中位耗时 (ms) | 占比 |
|---|---:|---:|
| **CFAR 检测** | **23.85** | **96%** |
| PPI LUT 散射 | 0.53 | 2% |
| 矩阵反投影 | 0.28 | 1% |
| PPI 3×3 膨胀 | 0.16 | <1% |
| SQLite 写航迹 | 0.08 | <1% |
| 航迹关联+滤波 | 0.03 | <1% |

### 剖析结论

用 `cProfile` 定位，23.85 ms 全部耗在 `detect_targets` **一个 Python 循环**里：
它先把 17424 个栅格全排序，再逐个做非极大抑制，
每帧要试 **8712 个候选**才凑够 8 个目标。

这跟语言**没有关系**——是算法写错了。

### 修复后（六行 numpy）

| 环节 | 修复前 | 修复后 | 加速 |
|---|---:|---:|---:|
| CFAR 检测 | 23.85 ms | **1.25 ms** | 19× |
| **每帧合计** | **24.93 ms** | **2.27 ms** | **11×** |
| 占 20 fps 预算 | 50% | **5%** | — |

修法：`np.argpartition` 只取最强 `max_targets × 12` 个候选，而不是全排序。
抑制逻辑原样保留，测试全绿。

---

## 决策

**不重写为 Rust。** 保持 Python + numpy + PyQt5。

---

## 理由

1. **瓶颈不在解释器，在算法。** 修完算法后每帧只用 5% 预算。
   真有性能问题时，下一个瓶颈也不会是"Python 慢"，而是"栅格太大""设备太多"，
   这些用降采样/降帧率就能解决，比换语言便宜两个数量级。

2. **热点本来就在 C 里。** numpy 的散射、积分图、FFT 全是 C 实现。
   把 Python 换成 Rust，这部分**一点也不会变快**——它已经是 C 的速度。

3. **这个项目的复杂度在"适配"，不在"算力"。** 
   9 个驱动、5 种传输、6 种形态、插件、标定。Rust 的类型系统能减少一类 bug，
   但解决不了"新雷达协议长什么样"的问题；反而每次加设备都要写 trait + 实现 + 编译，
   迭代速度掉一个档次。

4. **UI 是变更最频繁的部分（约 3000 行），Rust GUI 生态不适合这种场景。**
   egui/iced 画这种密集自绘 HUD 要手写布局与命中测试，
   PyQt 有现成的 QPainter/布局/样式表，改一版界面的成本差 3–5 倍。

5. **已经交付了可运行的 exe。** 重写等于把 13 组测试、9 个驱动、
   所有踩过的坑重新走一遍，用户可感知的收益为零。

---

## 考虑过但未采纳的方案

| 方案 | 评估 | 结论 |
|---|---|---|
| 全量 Rust 重写（含 egui） | 3–4 个月，收益不可见，UI 迭代变慢 | 否 |
| Rust 写核心 + Python 写 UI | 两套构建链、两套 FFI、跨语言调试 | 否 |
| **PyO3 只把热点编译成扩展** | 保留 Python 外壳，热点提速 5–20× | **备选**，见下 |
| Cython 同上前提 | 构建简单些，性能提升有限 | 备选 |
| 纯 Python 优化算法（本次采用） | 零依赖、零风险、11× | **是** |

---

## 什么时候应该重新考虑

给出可量化的触发条件，避免以后拍脑袋：

- 单帧固定开销 **> 16 ms**（60 fps 预算）且降采样无效
- 单实例需要同时处理 **> 1000 个目标**，或 **> 12 台设备**
- 需要在 **树莓派 / Jetson** 等资源受限设备上跑采集内核（内存 < 200 MB）
- 真信号处理（原始 ADC → FFT → MTI）成为主干，且 numpy 的临时数组分配成为瓶颈

到那时优先走 **PyO3**：只把 `_cfar_background`、融合散射、PPI 渲染
这三个热点编成 `radarscope._fast`，Python 侧调用不变。这样：
- 保留 Python 的适配灵活性（新驱动照样 150 行）
- 只优化真正热的 3 个函数
- 单文件轮子，`pip install` 即可，不破坏现有打包流程

**目前这些条件一个都不满足**，所以不做。

---

## 后果

- 继续用 Python，维护成本低、迭代快
- 性能问题按"先量、再改算法、最后才考虑换语言"的顺序处理
- `tools/bench.py` 成为常规工具：任何性能改动前后都跑一次，数字说话

## 参考

同类开源项目的技术选型也印证这个判断：

| 项目 | 语言 | 说明 |
|---|---|---|
| TI mmWave Industrial Visualizer | Python + PyQt5 | 官方工具，性能足够 |
| RadarStream | Python + PyQt5 + PyTorch | 处理原始 ADC，实时 |
| Exodus Radar（船用 PPI） | Python + numpy + tkinter | 8 fps PPI，跑在树莓派 |
| PyCINRAD | Python | 气象雷达业务级解码 |

没有一个因为"性能"改用 Rust。它们的性能瓶颈都在数据处理策略上，不在语言。
